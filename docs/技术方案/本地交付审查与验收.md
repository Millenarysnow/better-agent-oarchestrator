# 本地交付审查与验收

本文规定不创建 PR 的本地任务如何使用内置审查者、提交验收并进入看板后续阶段。工作区基线见 [本地项目基线与远端解耦](本地项目基线与远端解耦.md)，进程与持久化边界见 [architecture.md](../architecture.md)。

## 目标与非目标

**本地提交可以形成完整的交付、审查、返工与验收闭环。** 本地流程不要求远端、GitHub 登录、推送或 PR；审查者仍由项目已有 reviewer 角色配置选择，保留 Chat/TUI、模型、恢复与取消能力。

**审查、验收和发布是不同事实。** worker 报完成表示提交验收，reviewer 给出代码审查结论，协调者或用户决定验收是否通过。验收通过不授权合并或推送，也不自动关闭 worker。

**现有 PR 评审保持独立语义。** 本地任务不能通过伪造 PR URL 接入旧流程。第一版支持单 Git 仓库的已提交代码与资产；无仓库任务和多仓库任务需先定义版本集合后才能启用本地审查。

## 核心方案

**在现有审查引擎中增加明确的本地审查目标，复用 reviewer 生命周期。** 本地目标引用一次交付及其固定基点、目标提交和完成报告；PR 目标继续引用平台 PR。两者共享启动、取消、恢复、结果记录和界面，分别解释审查范围和反馈目的地。同一 reviewer 从 PR 目标切换到本地目标时重建执行上下文，防止沿用要求发布 PR 评论的旧系统指令；其他目标仍在运行时先明确取消，不能暗中终止它。

**本地结果由 daemon 可靠交付给协调者。** PR 评审仍通过平台评论反馈；本地审查不执行平台发布，结构化结果保存在本机并由既有协调消息机制传递。重启和重试不能造成重复返工。桌面完成通知以本地交付为对象，不要求 PR；通过通知仍明确提醒需要单独验收。

## 两个独立的本地开关

**项目增加“自动审查本地交付”和“Worker 主动请求本地审查”，均默认关闭。** 两者放在项目常规设置的“本地审查”区域，提供完整中文标签与解释；不能借用 PR 开关，否则开启本地能力会意外启动远端流程。

**自动审查只检查已提交验收的本地交付。** worker 处于空闲、完成报告已提交、版本仍匹配且该版本没有有效审查时，daemon 才启动审查。单纯空闲不表示任务完成，不能把每次回复间隙当成交付。

**主动请求开关改变新 worker 的职责指令。** 启用后，worker 在完成自验并提交完整完成报告后请求本地审查；关闭时由用户或协调者明确发起。两个开关同时开启仍只启动一次同版本、同审查者的审查。

**会话保留启动时的本地自动审查选择，并允许单独调整。** 项目设置变化影响新会话，不能悄悄改变旧任务的运行约定。旧项目及旧会话迁移后保持关闭。

## 交付与版本身份

**完成报告与交付版本必须在同一事务中落库。** 本地交付记录来源报告、不可变的比较基点、完成提交和目标分支。报告送达确认仅代表消息收到，不能作为审查或验收结论。升级前的报告不追补当前 HEAD；需新报告建立交付，避免把后来的代码冒充原交付。

**提交验收以干净、已提交的工作树为边界。** daemon 验证 Git 状态并解析完整 SHA，不自动提交、stash、切换分支或清理文件。尚未保存或提交的 UE 资产不能被当作已验收版本。

**审查读取固定提交之间的内容。** 不随着 worker 后续修改或目标分支移动而改变本次范围；工作树仅提供 Git 对象和阅读上下文。新提交、新的人类或协调者任务指令以及工作树未提交改动都会使当前交付失效，不能把旧版批准套到新版。看板采用 observer 最近观测的 Git 事实，发起审查与验收另行实时核验。

**同一报告、同一版本的重试必须复用交付身份。** 同一版本主动请求与 daemon 扫描并发时共用审查引擎的串行化与幂等判断。返工后的完整完成报告建立下一次交付，保留此前记录。

## 审查与验收职责

**协调者先检查完成报告，再按项目规则组织审查。** 默认人工发起路径支持检查报告是否齐全；本地自动开关表示明确允许 daemon 或 worker 在交付条件满足后发起。报告缺失、版本不一致或工作区脏时返回可解释错误，不默默审查其他版本。

**reviewer 只读代码与证据，输出阻塞问题、非阻塞建议和未验证范围。** 构建、测试和自动化验收由 worker 完成，审查者不在共享工作树中运行会改动文件的程序。指南是审查依据，不能覆盖只读职责和系统提交协议。

**二进制资产不能凭文件存在宣称审查通过。** 蓝图、模型和编辑器行为需要引用对应版本的验证证据；缺少证据的范围明确留待人工验收。

**本地审查结果优先交给协调者决定下一步。** 不把 reviewer 的所有建议直接视为 worker 必须执行的指令。阻塞项才能触发返工，非阻塞项随交付保留，由用户决定。

**验收操作必须指定当前交付。** 接受、退回或请求用户决定都由 daemon 验证版本和记录结论；worker 的完成声明不能自我批准。旧版本审查晚到时只保留历史，不能覆盖新交付。

**每个 worker 会话的阻塞性返工最多一轮。** 第一次完整审查后协调者可退回一次；返工提交后复核问题。再次出现阻塞进入待用户决定，不能继续自动循环。取消、审查进程退出和审查失败均不代表通过。多位审查者并行时分别取各自最新结论，任一仍在运行、有阻塞或失败，均不能被另一位的批准覆盖。

## 看板与用户界面

**看板位置由交付事实推导，运行状态独立展示。** daemon 计算本地交付阶段，renderer 不保存或自行猜测看板状态；否则桌面、CLI 与重启恢复会出现不同结论。

| 当前事实 | 本地看板行为 |
| --- | --- |
| 尚未提交验收，或已明确退回返工 | 开发中 |
| 已提交验收，等待开始审查 | 评审中，显示待审查 |
| reviewer 排队或运行 | 验证中，显示审查进度 |
| 审查结束或失败，等待验收或用户决定 | 评审中，显示实际结果 |
| 当前交付已明确验收通过 | 就绪，显示待合并 |
| 会话已终止 | 归档，保留交付与审查历史 |

**没有 PR 也显示本地评审入口。** 会话评审面板允许查看本地交付、启动或取消审查、阅读完整结论并执行验收。旧版“没有 PR 就隐藏全部控件”的条件必须限定到 PR 区域。

**合并继续由现有工作流完成。** 本次不新增自动 merge、push 或删除分支；归档不能被解释成验收通过。历史记录保留“未验收、通过、退回、待决定”等结果以解释收尾。

## 结构与依赖边界

**`domain` 与 SQLite 保存事实，`internal/review` 解释审查任务。** 本地交付、验收和审查目标通过新迁移加入；SQL 查询与生成代码遵循现有 sqlc 边界。变更事件继续来自数据库触发器。

**`service/review` 组织本地目标和结果回传，`autoreview` 决定是否自动启动。** reviewer 适配器、启动提示词和任务授权清单必须理解本地目标，不能仅删掉无 PR 检查就继续执行 GitHub 提交指令。

**HTTP 是桌面与 CLI 的共同写入边界。** 新操作扩展已有 reviews API，CLI 保持薄客户端；OpenAPI 与前端类型从源代码再生成。设置、会话指令与本地审查面板使用相同配置含义。

**全部运行材料位于 AO 数据目录。** 审查提示词、结果、暂存内容和验证数据不能写入用户项目或 OS 默认应用数据目录。桌面验证和打包测试使用隔离数据，不迁移正在运行的真实数据库。

## 被否决的方案

**仅移除 PR 前置检查被否决。** 旧提示词、授权清单、结果提交和反馈路径都依赖 PR，这样只会把失败推迟到 reviewer 启动之后。

**把 done 或报告 acknowledged 直接映射成就绪被否决。** 两者没有表达独立审查或验收决定，会把 worker 的完成声明当成用户认可。

**从聊天文本推测“已审查”“已合并”被否决。** 文本不可稳定关联提交，也不具备幂等和恢复语义；状态必须依赖结构化事实。

**为本地任务复制一整套 reviewer 运行时被否决。** 两套进程、恢复和模型配置会迅速分叉；只增加目标与回传差异，复用已有生命周期。

## 扩展准入

**多仓库和纯产物审查需要独立的版本身份设计。** 扩展前必须明确每个仓库提交或产物快照如何绑定同一交付，以及部分失败时如何处理，不能用根仓库一个 SHA 代表全部内容。

**自动识别合并只能增加可核验的合入事实。** 后续实现需区分普通 merge、squash 和 cherry-pick；提交数归零或会话关闭不能被当作合并证明。
