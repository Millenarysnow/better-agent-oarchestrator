# OpenCode 2 聊天接入与界面切换

本文说明 OpenCode 2 如何使用 AO 的结构化 Chat，以及如何在终端与 Chat 之间继续同一原生对话。报告送达另见 [OpenCode2终端报告可靠投递](OpenCode2终端报告可靠投递.md)，controller 所有权与恢复边界见 [架构说明](../architecture.md)。

## 目标与非目标

**启用已有终端会话的 TUI/Chat 双向切换，保留原生上下文与可见历史。** 新建 Chat、恢复 Chat 和切换既有终端必须使用同一套 OpenCode 2 驱动；不能只放开菜单而让后台新建空对话。

**终端报告投递继续独立工作。** 用户可以持续使用原生终端，worker report 仍由终端插件接纳；选择 Chat 不是接收报告的前提。

**不将 OpenCode 1 会话自动转换为 OpenCode 2。** 两个 major 的二进制、存储根目录和持久 Chat 身份继续隔离。原生历史的编辑、丢失记录的补造及跨项目对话迁移不在本方案范围内。

## 核心方案

**复用现有 `opencodev2acp` 与通用 ACP transport，补齐终端适配器的 `AgentInterfaceHandoff`。** 注册 Chat driver 只表示可以创建结构化对话；界面切换还需要适配器声明两种 controller 能打开同一原生会话，这正是当前菜单不可用的缺口。

**TUI 和 ACP 使用同一个隔离的 v2 data home，controller 串行接管。** 官方 [ACP 文档](https://opencode.ai/docs/cli/acp/) 规定 `opencode acp` 自带私有服务，通过 stdio 通信；不要给它臆造终端专用参数，也不要连接共享后台服务。

**以 ACP `session/load` 重放原生历史作为 TUI→Chat 的完成屏障。** `session/resume` 成功只证明 controller 可继续，不能证明 UI 已获得历史；缺少历史能力、加载失败或不满足既有检查点时，沿用现有切换回滚与恢复路径。

## 结构与依赖边界

**终端适配器拥有原生身份转换与历史存在性探测。** `adapters/agent/opencodev2` 将 hook 的原始 ID 转成 Chat 能接受的句柄，并在恢复命令和原生导出之前还原 ID。其它层不拼接 OpenCode CLI 参数。

**`session_manager` 继续拥有切换事务。** 它负责本代原生身份确认、准入、停止源 controller、提交 controller epoch、启动目标及恢复失败；前端仍按 daemon 给出的能力与原因显示入口。

**Chat service 继续拥有历史投影和检查点验证。** ACP 事件进入通用 projector，不能通过复制终端渲染文本代替原生历史，也不能为了启用 OpenCode 而关闭其它 harness 的历史完整性检查。

**AO 自己的句柄封装属于身份表达，不属于新的原生会话。** domain 层只提供同 harness 下原始 ID 与 AO 封装 ID 的相等判断；它不访问 provider、不放宽恢复准入，也不让 v1 标签匹配 v2。

## 原生 ID 与 Chat 句柄

**原生 ID 是 OpenCode 的 `ses_…`，持久 Chat 句柄带 `ao-harness:opencode-v2:` 前缀。** 终端 hook 继续携带原始 ID。handoff 返回带标签的标准句柄，使目标 ACP 保持现有 major 校验；终端恢复与历史探测同时接受原始 ID及正确的 v2 句柄。

**持久 Chat 恢复仍拒绝无标签或其它 major 的句柄。** 允许历史终端的原始 ID参与身份关联，不等于允许 Chat 将任意旧 ID当作 v2 会话。转换只发生在 v2 适配器声明的 handoff 边界。

**同一对话的两种表示不能触发原生身份变更。** 生命周期 reducer 与 Chat 检查点用同 harness 的身份等价关系比较；否则一次正常往返会误清除未解决的检查点，或把真实用户输入误判为另一条对话。不同原生 ID和不同 major 仍是不等价身份。

**终端 turn 的清理使用源终端保存的 ID。** 只有目标 Chat 成功导入原生历史后，才清理该源线程的终端副本；不能拿带标签的 Chat 句柄去删除按原始 ID记录的 turn，也不能删除其它原生线程的历史。

## 活动通知与历史检查点

**OpenCode 2 的 execution/status 通知表示活动状态，不证明一对用户输入与模型回答。** 当前插件没有提交用户文本或可靠的回合身份；据此制造“缺失 prompt 的 Stop”会永久阻塞原生历史接管。纯观察通知保留已有检查点，由原生历史重放证明对话内容。

**旧版本留下的纯观察型未解决标记不构成用户回合证据。** 仅在 v2、检查点为空或 legacy、没有回合身份、文本、用户提交时间和原生证据时，Chat 可按活动观察处理该标记。只要存在真实输入或检查点证据，仍须通过完整的原生历史核对，不能用这个兼容路径消除它。

**AO 的用户输入与历史高水位始终是独立屏障。** 通过 AO 发送的用户文本、可信回合边界和先前 Chat 保存的历史，不能被一个 provider 空闲事件或一次成功 load 覆盖。重放缺失最新用户输入或已有消息时必须拒绝接管。

**报告仍是协调消息。** 原生队列中的 report envelope 可在历史里重放，但不得因此伪造用户亲自提交的终端检查点。

## 切换与失败行为

**本代终端的身份必须由已接受的 hook 确认。** 保存过原生 ID并不证明当前屏幕仍在该对话；未经确认的恢复、启动中会话和身份缺失继续阻止切换。

**原生导出使用精确 ID、相同 workspace 和 v2 data home。** 探测失败不是“对话不存在”的证据。只有现有的未开始对话证明成立时，才允许目标从空会话开始。

**停止源 controller 必须先于目标启动。** 存活状态不确定时进入恢复状态，不同时运行终端与 ACP 写同一个原生会话。取消、queued message 和 daemon 重启继续由既有切换状态机处理。

**返回终端使用原生恢复，不重放任务提示创建替代对话。** 恢复出的终端必须重新确认自己的 launch ID；报告桥接只绑定这个新 generation，旧 controller 不能继续接收报告。

**支持切换不保证当前一定可切。** 忙碌、权限决定、认证失败、未保存草稿和历史不一致仍按现有产品规则显示具体原因，不能通过前端强制启用入口绕过。

## 被否决的方案

**只修改灰色菜单被否决。** 前端无法提供原生身份、历史重放与单 controller 保证，后台仍会拒绝，或丢失对话上下文。

**让 ACP 接受所有无标签 ID被否决。** 它会撤销已建立的 OpenCode major 隔离。终端原始 ID应经适配器转换，持久恢复继续校验标签。

**一律忽略未解决检查点被否决。** 真实用户输入可能尚未持久出现在 provider 历史里。兼容条件只涵盖没有任何回合证据的 v2 活动观察，不能扩展到有输入或历史高水位的情况。

**将 Chat 看作终端的第二个并行控制器被否决。** 两个进程同时写同一原生会话会造成重复执行、权限响应错位和不可判定的恢复。

## 未实现的部分与扩展准入

OpenCode 2 专用的历史编辑、跨 major 迁移以及更完整的终端回合观察暂缓。新增终端文本或回合证据必须同时证明其原生身份、持久性与乱序行为；不能把 pre-admission hook 当成消息接纳证明，也不能降低报告投递方案的去重保证。
